# Calendly appointment booking

Calendly is an optional provider adapter for installations that already use
Calendly. It is not Ava's generic appointment-booking layer and it is not
required for booking. Direct API booking requires a paid Calendly plan. For a
self-hosted calendar exposed through Streamable HTTP MCP, start with
[Appointment booking providers](Appointment-booking-providers.md).

Release qualification and accepted limits are recorded in the
[v7.7.0 validation matrix](baselines/golden/v7.7.0-validation-matrix.md).
Before upgrades, preserve the journal and managed credentials using the
[integration backup guide](INTEGRATION_BACKUPS.md); application rollback must not
erase remote-submission replay barriers.

Calendly v1 connects one operator-owned Calendly user to self-hosted AVA Core. Agents can offer times and book existing supported one-to-one appointments. Calendly owns calendar connections, appointment settings, invitations, and subsequent cancellation/rescheduling.

## Setup

1. Open **Tools → Calendly** in the authenticated Admin UI, preferably through HTTPS or an encrypted SSH tunnel. Do not paste a token into a chat, prompt, YAML, or support ticket.
2. Create a personal access token in Calendly's **Integrations → API & Webhooks**. Select `users:read`, `event_types:read`, `availability:read`, and `scheduled_events:write` (which includes scheduled-event read). Direct booking requires Standard or higher; a new trial has a much smaller booking allowance.
3. Enter the token, **Verify connection**, then **Save connection**. Verification is read-only. Saving pauses scheduling until you explicitly enable it. Invalid replacements leave the existing token intact; an interrupted file replacement leaves scheduling disabled.
4. **Refresh from Calendly**, confirm that the intended types are one host/one invitee, and select supported appointments. Configure Google/Microsoft calendar connections, conflict calendars, destinations, notifications, and reminders in Calendly.
5. Enable the tool, save the appointment selection, and use the Tools page's save/apply action. In **Agents → Edit → Tools**, enable `calendly_calendar` and select the permitted appointment types. Existing agents are not automatically assigned this tool.
6. Preview setup test times while booking is paused. After approving the exact test details, enable booking in the connection panel and run the explicit setup test with your own recipient. Creation makes a real appointment and can send a real invitation; Verify, Save, Refresh, Apply, and finding test times do not.
7. Check the actual calendar destination and invitation, inspect the management links, and **Verify tracking readback**. Record the operator checks and clean up the test through Calendly. Test a real call separately before enabling an agent for callers.

Conference kinds (Google Meet, Teams, Zoom) need a successful explicit setup qualification before normal call booking. Other supported locations are none, one fixed physical/custom location, or a fixed inbound host phone. Unsupported entries explain their limitation. Group/pooled/paid/variable-duration appointments, required multi-select questions, multiple locations, guests, and SMS opt-in are excluded initially.

## Caller behavior

“Next available” requires the caller's timezone, but no preferred date. The native `get_available_slots` action defaults omitted dates to server time plus one minute through seven days later, returning earliest times first. A supplied start without an end searches seven days from that start. Explicit windows remain future-only and at most 31 days; for a particular local day, use local midnight to next midnight with the correct UTC offsets. An empty response describes only the searched window: ask before looking later. Missing/invalid inputs produce corrective guidance and do not submit a booking. Booking still requires an opaque returned slot reference, the canonical recap, and fresh caller approval.

The tool has three actions: `list_appointment_types`, `get_available_slots`, and `create_booking`. Action values are arguments to `calendly_calendar`, not separate functions.

The agent asks for purpose, timezone, name, exact invitation email, and required appointment questions. Its first `create_booking` request prepares a canonical recap without submitting an appointment. The agent spells the returned email, including every dot and symbol, reads the full appointment/date/time/timezone/duration/location/name/recipient recap, and waits for final approval. Only a second request with that recap's short-lived `confirmation_reference`, unchanged details, and both confirmation flags can submit. A changed detail requires a new recap and fresh approval. The backend accepts only its own call-bound slot/confirmation references and rechecks current availability and metadata before booking. These guards bind submitted data to a recap; the voice acceptance test must still check that the agent actually reads it and waits for the caller.

The native tool remembers the latest validated recap details only in the active call's private memory, for up to five minutes. Its final request may contain just the exact `confirmation_reference` and both fresh approval flags. It never inherits approval from preparation. Explicitly repeated changes still fail the recap digest check; corrections replace the pending reference. The cache is excluded from session serialization/repr, is not written into the journal or Call History, and disappears with the call; SQLite continues to store only the confirmation digest. If memory or the reference is unavailable/stale, prepare a new recap and obtain fresh approval. This is a validation problem, not evidence that a time is busy.

At most one confirmed or uncertain booking operation is permitted per call. Repeated tool calls return the retained original result. They do not change its time or recipient. Later changes, including requests made in the same conversation after booking, use Calendly's confirmation link or staff. An error checking availability is not a busy slot. Booking success is not proof of delivered email or accepted RSVP.

If a new call selects the same appointment, time and recipient as an earlier canceled booking, AVA may release that cross-call duplicate barrier only after exact event and invitee reads both prove cancellation and match the saved host, appointment, time, duration, recipient and tracking marker. Missing data, active/uncertain/rescheduled records, mismatches, 404s and read failures keep it blocked for staff. The original operation remains a replay barrier; no history is deleted. Fresh availability, final approval, active-call and connection checks still precede the single booking POST. Recaps carry a server-computed `spoken_date` so the local weekday agrees with the date.

## Pending submissions

AVA commits its submission journal before one booking POST. It never automatically repeats a POST after a lost response, timeout, server error, cancellation, or process restart.

When setup has qualified tracking readback, AVA can search a narrow host/recipient/time window and confirm exactly one matching opaque attempt marker. Missing, incomplete, ambiguous, changed, or inaccessible records require staff. No result is never proof that a previous submission failed. There is no exactly-once claim against Calendly or other booking applications.

**Pending requests and setup results** loads retained requests on entry; use **Refresh pending requests** if loading fails. Use this panel to inspect retained outcomes, run a bounded status check, open Calendly, or record external handling. An external-resolution note remains operator evidence; it does not make a fresh submission from the old call safe. Call History also shows the recorded booking outcome and a link to recovery. It is not a continuously synchronized booking dashboard.

**Disable booking now** prevents new submissions from active as well as new calls, while retaining credentials for read-only recovery. A previously admitted request may finish. **Disconnect** removes the local token and closes scheduling; it never cancels existing appointments or deletes pending history. A different-account reconnect invalidates old resource assignments and proposals.

## Storage, privacy, and recovery

The token lives in `secrets/calendly-default-token.json`; the integration journal lives in `data/operator/calendly.db`. Both services use the existing shared mounts and intended UID 1000, with restricted file access. No token is returned by the connection API or ordinary config reads. Neither file belongs in Git or a public support bundle.

SQLite WAL/FULL synchronization and transactional claims provide local submission durability. A missing, locked, unreadable, incompatible or failed journal stops booking rather than falling back to memory. A shared rate-limit cooldown pauses recovery without consuming its automatic check budget. Private lookup details and free-text resolution notes expire after 30 days, or earlier configured positive Call History retention; call-history purge scrubs linked details while preserving replay barriers. Expired details require manual Calendly investigation.

Once a Calendly journal, saved Calendly credential, or `calendly.db.configured` privacy marker exists, Call History deletion records linked erasure work atomically in its own database. New history written on installations that never initialized Calendly does not create provider-specific cleanup obligations. Unset or empty `CALENDLY_DB_PATH` and `CALENDLY_TOKEN_PATH` use the standard journal and credential paths. Opening an existing journal during upgrade or recovery backfills the non-secret `calendly.db.configured` privacy marker, including for connections disconnected before upgrading; resaving a token is not required. Disconnect persists this marker before removing the credential. Preserve it with the journal and Call History database across upgrades and recovery. If the journal file is temporarily absent after this backfill, individual and retention deletion still complete and the minimal call-ID work item survives restart even without a saved credential; recovery retries the scrub and removes the work item only after an actual journal scrub succeeds. History written before this upgrade retains its previous erasure guarantee through an additive internal flag in the Call History database. Individual and retention deletion queue those legacy call IDs even if the journal, credential and marker are all absent before the first upgraded process starts. This bounded compatibility scope can retain erasure work for old calls on previously unused installations because missing adapter files cannot prove that Calendly was never configured. New history written by upgraded code uses the adapter footprints instead; older writers remain conservative after a code rollback. Restoring the original journal lets recovery scrub queued legacy calls without requiring a token or manual ordering of history deletion. Preserve the History database and its internal flag during recovery. Unreadable or invalid footprint paths are treated as possible prior configuration: deletion still queues erasure and completes, while recovery retains the obligation until storage is repaired. Existing queued work is retained even after Calendly is disabled. Deleted-call operations become immutable `erased` records, even if admission has not committed yet: later booking responses, reconciliation, staff resolution or duplicate-release checks cannot restore their details. Original-operation replay barriers remain; previously rejected, aborted or verified-canceled attempts do not gain a cross-call duplicate barrier during erasure. This does not cancel an upstream appointment; an already admitted request may still complete and staff must check Calendly. Queued erasure obligations do not expire without a successful scrub; processing is bounded to 100 IDs per pass. Operators should repair journal faults promptly. The recovery list and Call History show the same request reference so staff can match a recorded outcome to its pending request. Malformed provider readback remains uncertain and reaches staff handling after the bounded automatic checks; it never permits another booking POST.

Back up SQLite with its backup API or a consistent WAL-aware procedure. Preserve the journal through rollback. Before restoring an older backup, pause booking and review remote submissions after the backup; local restore cannot prove that they never occurred. Remove Calendly tool and agent-policy references before downgrading to code that does not recognize them. Do not delete real appointments or replay attempts during rollback.

Troubleshooting codes are diagnostics for operators, not scripts for the caller: `connection_disabled`, `credential_permissions`, `appointment_setup_incomplete`, `conference_not_qualified`, `proposal_changed_reconfirm`, `booking_capacity_busy`, `discovery_not_qualified`, `search_incomplete`, and `lookup_details_expired` all have fail-closed behavior. Resolve setup or verify the retained attempt before another booking.
